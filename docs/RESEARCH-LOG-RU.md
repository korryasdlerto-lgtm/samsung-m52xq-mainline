# Портирование postmarketOS на Samsung Galaxy M52 5G (m52xq) с mainline-ядром

## Статус: Фаза 0 — исследование и подготовка материалов (2026-08-02)

Это НЕ готовая пошаговая инструкция — реального bring-up ядра ещё не делалось.
Это честный журнал того, что уже найдено и скачано, и план того, что предстоит
сделать дальше. Документ будет пополняться по мере реальной работы.

## Цель

Портировать postmarketOS на Samsung Galaxy M52 5G (m52xq) с **настоящим
mainline-ядром** (upstream Linux, а не downstream/vendor Android-ядро) —
то есть полноценный Linux, а не Halium/libhybris-прослойка поверх Android-HAL,
как в текущем проекте (см. `/home/sasha/Templates/плазмамобайл/`).

Это принципиально другой, гораздо более фундаментальный подход, чем всё, что
делалось в проекте Halium/Plasma Mobile до сих пор: там мы обходили отсутствие
драйверов через Android-контейнер и libhybris-мост, здесь цель — чтобы
Linux-ядро само, напрямую, умело работать с железом устройства (GPU, дисплей,
тачскрин, модем, WiFi и т.д.), без Android вообще.

## Железо устройства

- **Модель**: Samsung Galaxy M52 5G, кодовое имя `m52xq` (варианты M526B/M526BR)
- **SoC**: Qualcomm **SM7325** (Snapdragon 778G 5G)
- **Внутреннее кодовое имя платформы Qualcomm**: `yupik` — подтверждено НЕ
  предположением, а прямой строкой из логов ядра ЭТОГО устройства, увиденной
  сегодня вечером в отдельном проекте (Halium/Plasma Mobile marathon):
  ```
  subsys-pil-tz soc:qcom,ipa_fws: yupik_ipa_fws: Failed to locate yupik_ipa_fws.mdt
  ```
  Это ключевая улика — она напрямую связывает эту SoC с семейством "yupik",
  к которому также относятся SC7280 и QCM6490.

## Почему mainline в принципе может быть реалистичен именно для этой SoC

Qualcomm SM7325/SC7280/QCM6490 — всё одна и та же платформа "yupik". Для
**Fairphone 5** (QCM6490, та же платформа) уже существует РЕАЛЬНАЯ,
смерженная в апстрим поддержка:

- `arch/arm64/boot/dts/qcom/qcm6490-fairphone-fp5.dts` — есть прямо в
  `torvalds/linux` (основной ветке ядра Linux), не в форке.
- Bring-up Fairphone 5 в апстриме отталкивался именно от существовавшей
  поддержки SC7280 — пришлось вынести ChromeOS-специфичные куски в отдельный
  `sc7280-chrome-common.dtsi`, чтобы завести ядро на обычной (не ChromeOS)
  плате со стандартным TrustZone.
- Источники (проверено через WebSearch/WebFetch 2026-08-02):
  - https://github.com/sc7280-mainline/linux — community-форк mainline-ядра
    именно под SC7280/SM7325/QCM6490
  - https://github.com/torvalds/linux/blob/master/arch/arm64/boot/dts/qcom/qcm6490-fairphone-fp5.dts
  - https://patches.linaro.org/project/linux-arm-msm/cover/20230919-fp5-initial-v2-0-14bb7cedadf5@fairphone.com/
    ("Initial support for the Fairphone 5 smartphone", патчи на Linaro)

Это НЕ означает, что M52 "почти готов" — Fairphone 5 и M52 это разные платы
с разной обвязкой (PMIC, экран, тачскрин, память, модем), и весь bring-up
конкретной платы всё равно придётся делать заново. Но общая SoC-часть
(CPU/GPU/interconnect/базовая инициализация платформы) уже имеет
работающий образец для подражания — это не bring-up "с нуля в вакууме".

другое устройство (хоть и той же линейки Samsung A/M-серии), и даже там не
факт, что используется настоящее mainline-ядро (может быть downstream).

## Материалы, скачанные в эту папку

### 1. `linux/` — mainline-форк ядра
```
git clone --depth 1 https://github.com/sc7280-mainline/linux.git
```
Размер: ~2.0 ГБ (shallow-клон, без полной истории).
Назначение: рабочая база mainline-ядра с уже существующей поддержкой
платформы "yupik" (SC7280/SM7325/QCM6490), включая наработки по Fairphone 5.
Именно отсюда предстоит брать device tree (`.dts`) как шаблон для платы M52.

### 2. `android_device_samsung_m52xq/` — device tree LineageOS 23.2
```
git clone --depth 1 -b lineage-23.2 https://github.com/LineageOS/android_device_samsung_m52xq.git
```
Размер: ~1.1 МБ.
Назначение: справочник по РЕАЛЬНОЙ, проверенной аппаратной конфигурации
именно этой платы — PMIC, распиновка, память, конфигурация ядра под Android
(`BoardConfig.mk`, `configs/`, `proprietary-files.txt` и т.д.). Используется
не для сборки Android, а как источник фактов о железе при написании
mainline device tree с нуля.

## План дальнейшей работы (не начато)

Это ориентировочный план, основанный на общей практике postmarketOS/mainline
bring-up (Fairphone 5, PinePhone и подобные проекты), а не проверенная
инструкция для конкретно M52:

1. **Изучить `android_device_samsung_m52xq`**: `BoardConfig.mk`, `configs/`,
   найти реальную модель PMIC, дисплейной панели, тачскрин-контроллера,
   раскладку памяти (UFS/eMMC).
2. **Сравнить с `qcm6490-fairphone-fp5.dts`**: понять структуру существующего
   рабочего DTS для платформы "yupik" как шаблон.
3. **Написать черновой `sm7325-samsung-m52xq.dts`**: адаптировать шаблон
   Fairphone 5 под найденную в п.1 конфигурацию железа M52.
4. **Собрать ядро** (`make ARCH=arm64 ... Image.gz-dtb` или аналог) под этот
   DTS.
5. **Тестовая загрузка**: скорее всего через fastboot boot (без прошивки в
   раздел), чтобы не рисковать кирпичом, аналогично уже отработанной в
   проекте Halium/Plasma Mobile осторожной методологии (см. память проекта
   `project_halium_runtime_boot` — там же описаны похожие меры
   предосторожности для этого самого устройства).
6. **Итеративный дебаг железа**: скорее всего UART/serial-console
   понадобится для первых попыток (mainline-ядро на новой плате почти
   никогда не грузится с первого раза).
7. Только после того как ядро реально грузится и есть базовая консоль —
   переходить к postmarketOS pmaports (создание нового `device/testing/`
   пакета, инициализация userland).

**Реалистичная оценка объёма**: это многонедельный/многомесячный проект
даже при наличии готового шаблона (Fairphone 5) — GPU, дисплей, модем,
WiFi на mainline для таких SoC почти всегда самые сложные и долгие части,
часто остающиеся неполными годами даже у активно поддерживаемых устройств.

## Обновление 2026-08-02 (позже вечером): реальные детали железа найдены

Изучен настоящий downstream device tree M52xq из
`LineageOS/android_kernel_samsung_sm7325` (ветка `lineage-23.2`,
`arch/arm64/boot/dts/samsung/m52/m52xq/m52xq_eur_open_w00_r05.dts`, без
клонирования — просмотрено через WebFetch). Файл сам себя описывает как
относящийся к "Qualcomm Yupik platform" — ещё одно прямое подтверждение.

Найдены реальные компоненты железа (для будущего сравнения с шаблоном
Fairphone 5 при написании DTS):

- **Зарядка/АКБ**: чип **SM5714** (заряд + fuel gauge), direct charging через
  **PCA9468**. Это ТОЧНОЕ совпадение с тем, что живьём наблюдалось в pstore
  логах устройства сегодня в отдельном (Halium) проекте — `sm5714-charger`,
  `pca9468_chg_set_property` и т.д. видны там же.
- **PMIC-регуляторы**: серия **PM8008** (доп. PMIC для питания периферии).
- **Экран**: панель **Novatek NT36672E**, 1080×2400 (FHD+), поддержка до
  144Гц/120Гц/90Гц с DFS (dynamic frame switching), DSC (display stream
  compression) включена.
- **Отпечаток пальца**: **ET523**.
- **Аудио**: подсистема Bolero (TX/RX/VA macro) + кодек **WCD938x** —
  совпадает со списком модулей ядра LineageOS (`wcd938x_dlkm.ko` и т.д.).
- Overlay применяется к ревизиям платы 0x05–0x20.

Также найден `BOARD_NAME := SRPUF17B001` в `BoardConfig.mk` — реальный код
платы/PCB.

### Первая пробная сборка mainline-ядра — запущена

В `linux/` (форк `sc7280-mainline`) обнаружился **готовый `fp5_defconfig`**
(конфигурация именно под Fairphone 5) в `arch/arm64/configs/` — помимо него
там только базовый `defconfig`, `hardening.config`, `virt.config`, ничего
специфичного под SC7280/QCM6490 в общем, только под FP5 конкретно.

Кросс-компилятор `aarch64-linux-gnu-gcc` уже установлен на хосте (проверено
`which`), отдельно доустанавливать не пришлось.

Запущено (2026-08-02, поздно вечером):
```
cd linux
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- fp5_defconfig   # успешно
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j12 Image.gz-dtb   # в фоне
```
Цель — не сборка РЕАЛЬНОГО образа под M52 (для этого ещё не написан DTS под
M52), а проверка, что сама связка (форк ядра + fp5_defconfig + кросс-тулчейн
на этом хосте) вообще собирается без ошибок — рабочая база для дальнейшей
адаптации под M52.

### Первая пробная сборка — УСПЕШНА

```
cd linux
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- fp5_defconfig
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j12 Image.gz-dtb   # цель Image.gz-dtb не определена в этом форке
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j12 Image          # ← собралось: 26 МБ
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j12 dtbs           # ← собралось (среди прочих)
```

**Результат (2026-08-02, поздно вечером): первая рабочая пара ядро+DTB для
платформы "yupik" реально собрана на этом хосте:**
- `linux/arch/arm64/boot/Image` — 26 МБ, собран без ошибок
- `linux/arch/arm64/boot/dts/qcom/qcm6490-fairphone-fp5.dtb` — 152 КБ,
  собран без ошибок

Это пока Fairphone 5, не M52 — но это подтверждает, что вся связка (форк
`sc7280-mainline/linux` + `fp5_defconfig` + кросс-тулчейн
`aarch64-linux-gnu-gcc` на этом хосте) рабочая от начала до конца. Реальная
следующая веха — написать `sm7325-samsung-m52xq.dts` на основе найденных
выше деталей железа (SM5714/PCA9468/PM8008/NT36672E/ET523/WCD938x) и
попробовать собрать УЖЕ под него.

Примечание: `make dtbs` без указания конкретного файла собирает ВСЕ `.dtb`
в дереве (включая сотни файлов под ноутбуки Windows-on-ARM на x1e80100/
x1p42100/x1p64100 — они есть в этом же общем qcom-дереве, но никак не
относятся к нашей задаче) — в следующий раз для скорости лучше указывать
конкретную цель: `make ... qcom/qcm6490-fairphone-fp5.dtb` вместо `dtbs`.

### Полный разбор `qcm6490-fairphone-fp5.dts` (шаблон) — что внутри

Прочитан целиком локально (файл уже в клонированном `linux/`). Ключевые
находки для будущей адаптации под M52:

- **Базовые инклюды**: `kodiak.dtsi` (SoC-уровень QCM6490/"kodiak" —
  видимо это mainline-имя для самой SoC, отдельное от "yupik") +
  `pm7250b.dtsi`, `pm7325.dtsi`, `pm8350c.dtsi`, `pmk8350.dtsi` (PMIC-чипы).
  У M52 судя по downstream DTS главные PMIC другие (PM8008 + чипы заряда
  SM5714/PCA9468, не входящие в этот список PMIC вообще) —規 придётся
  разбираться, есть ли для SM5714/PCA9468 готовые mainline-драйверы
  регуляторов/заряда, или их нет вовсе.
- **WiFi подключён через ШТАТНЫЙ mainline-драйвер** (`&wifi { status =
  "okay"; qcom,calibration-variant = "Fairphone_5"; };`), НЕ через закрытый
  vendor-модуль (какой используется в downstream/Halium-проекте —
  `qca_cld3_wlan.ko`). Если у M52 тот же класс WiFi-чипа (WCN67xx/68xx
  семейство), это потенциально решает главную нерешённую боль ВСЕГО
  вечера в параллельном Halium-проекте (WiFi/WPSS вообще не грузится там
  из-за закрытого драйвера) — но требует проверки, что чип M52 действительно
  из поддерживаемого в mainline семейства.
- **GPU zap-shader**: `firmware-name = "qcom/qcm6490/fairphone5/a660_zap.mbn"`
  — Adreno **a660**, то же самое GPU-поколение, что упоминалось в отдельном
  Halium-проекте сегодня вечером (там был известный "a660_zap-shader-
  fallback" гонка при старте GPU-моста) — ещё одно прямое пересечение
  находок между двумя проектами.
- **Экран**: `fairphone,fp5-rm692e5-boe`, `raydium,rm692e5` (Raydium панель)
  — у M52 своя, Novatek NT36672E (см. выше) — панель точно другая, нужен
  отдельный mainline-драйвер под NT36672E (или писать новый).
- **Тачскрин**: Goodix gt9897, SPI — у M52 Synaptics/STM (см. список
  модулей LineageOS выше) — тоже другой, нужен отдельный драйвер.
- **Найдена прямая улика активной апстрим-работы именно над SM7325**: в
  самом конце файла —
  ```
  // TODO: Figure out TX macro versions
  // See https://lore.kernel.org/linux-arm-msm/20260526-sc7280-tx-macro-v1-0-1aad6900fec0@fairphone.com/t/
  &lpass_tx_macro {
      compatible = "qcom,sm7325-lpass-tx-macro", "qcom,sm8450-lpass-tx-macro";
  };
  ```
  То есть апстрим-разработчики (примерно май 2026) УЖЕ добавляют
  `qcom,sm7325-lpass-tx-macro` как отдельную совместимость — прямое
  свидетельство, что SM7325 начинает получать специфичную поддержку в
  mainline, не только через "тот же QCM6490". Сама ссылка на
  lore.kernel.org недоступна для чтения (та же защита Anubis, что и на
  вики postmarketOS) — стоит попробовать открыть вручную в браузере, там
  может быть дополнительный контекст/участники обсуждения.

- Реальный `pmaports`-пакет `device-samsung-m52xq`, судя по командам
  установки на странице (`pmbootstrap install --android-recovery-zip`,

  поиск через GitLab API по `device/` в `pmaports` его не нашёл с первой
  попытки — возможно, лежит не в стандартном пути или в отдельной
  ветке/MR, не влитой в main) — не критично для нашей mainline-задачи,
  но стоит поискать отдельно, если понадобится ссылка на исходный APKBUILD
  этого пакета.

M52-специфичный, с проверкой наличия mainline-драйвера для каждого перед
переносом.

### `pmbootstrap install`: полная хронология отладки сборки (2026-08-02, ночь)

После создания `device-samsung-m52xq`/`linux-samsung-m52xq` запущена
настоящая сборка (`pmbootstrap install`). Она падала **семь раз подряд**,
каждый раз по-разному, но это НЕ случайные/флаки-ошибки — каждая причина
была реальной, и с каждым разом сборка проходила дальше по конвейеру.
Полная хронология (важно для будущих попыток, чтобы не наступать на те
же грабли):

1. **Пароль пользователя навсегда завис**: `pmbootstrap install` в какой-то
   момент спрашивает пароль для системного пользователя `user` внутри
   будущего rootfs. Скрипт-автоответчик слал пустые строки (`yes ''`),
   а пустой пароль не принимается — уходило в бесконечный повтор вопроса.
   **Фикс**: слать реальный непустой пароль (`printf 'pass\npass\n'`,
   дважды — подтверждение).

2. **`[Errno 2] No such file or directory: 'modprobe'`**: не хватало
   пакета `kmod` в самом Docker-образе (`pmb-env`), из которого
   запускается `pmbootstrap`. **Фикс**: добавить `kmod` (и заодно
   `qemu-user-static`, `binfmt-support` — нужны для сборки под aarch64 на
   x86_64-хосте) в `Dockerfile.pmb`, пересобрать образ.

3. **`ERROR: : Could not find it in pmaports or any APKINDEX!`** (имя
   пакета пустое, до двоеточия ничего нет) — самая коварная ошибка,
   потрачено больше всего времени. Проверено и отброшено:
   синтаксис `depends=` в собственных APKBUILD (в порядке); гипотеза, что
   баг специфичен для канала `edge` ("rolling release / occasional
   breakage") — переключились на стабильный `v26.06`, **ошибка
   повторилась один в один**, значит канал ни при чём.
   **Как реально нашли причину**: временно вставили
   `import traceback; traceback.print_stack()` прямо в
   `pmb/build/_package.py` перед местом, где кидается эта ошибка (внутри
   `pmb-env`-контейнера, файл живёт в смонтированном томе — правится
   прямо на хосте, без пересборки образа). Стек вызовов показал:
   `pmb/install/_install.py` → `pmb.chroot.apk.install(install_packages, chroot)`
   — то есть проблема не в глубине дерева зависимостей, а в САМОМ
   первом списке пакетов на установку. В `_install.py` нашли строку:
   ```python
   if context.config.extra_packages.lower() != "none":
       install_packages += context.config.extra_packages.split(",")
   ```
   Наш `~/.config/pmbootstrap_v3.cfg` содержал `extra_packages = ` —
   **пустую строку**, не `"none"` — а `"".split(",")` в Python возвращает
   `['']` (список из ОДНОЙ пустой строки), которая и попадала в список
   пакетов на установку как несуществующее имя пакета. Ирония в том, что
   эту пустую строку туда вписали МЫ САМИ — при более раннем ручном
   исправлении рассинхрона ответов `pmbootstrap init` (см. ниже), решив,
   что "просто убрать значение" эквивалентно "none". Не эквивалентно.
   **Фикс**: `extra_packages = none` явно (текстом, не пусто).
   После находки debug-патч (`traceback.print_stack()`) убран обратно.

4. **`ERROR: Couldn't build aarch64/linux-samsung-m52xq-7.1.2-r0.apk!`**
   — первая ошибка, для которой реально пришлось лезть в
   `/root/.local/var/pmbootstrap/log.txt` (не в основной вывод
   `pmbootstrap`, а в его подробный внутренний лог) — там нашлось
   настоящее сообщение сборки ядра: сборка реально дошла до компиляции
   (несколько сотен файлов, включая `drivers/gpu/drm/msm/*` — GPU-драйвер)
   и упала на:
   ```
   GENHDR  drivers/gpu/drm/msm/generated/a2xx.xml.h
   /bin/sh: python3: not found
   ```
   Генерация заголовка для Adreno GPU (`a2xx.xml.h`) в этом ядре делается
   Python-скриптом, а `python3` не был указан как build-зависимость в
   нашем `linux-samsung-m52xq/APKBUILD` (`makedepends=`). **Фикс**:
   добавить `python3` в `makedepends`.

5. **`ERROR: Couldn't build aarch64/device-samsung-m52xq-1-r0.apk!`** —
   `/home/pmos/build/deviceinfo: FAILED`, `sha512sum: WARNING: 1 of 1
   computed checksums did NOT match`. Причина простая: `sha512sums=` в
   `device-samsung-m52xq/APKBUILD` были посчитаны РАНЬШЕ, чем в
   `deviceinfo` добавили `deviceinfo_drm="true"` (см. выше, для показа
   Plasma Mobile в списке UI) — контрольная сумма протухла. **Фикс**:
   `pmbootstrap checksum device-samsung-m52xq` заново, ПОСЛЕ всех правок
   файла, не раньше.

### КРИТИЧЕСКАЯ НАХОДКА: наш DTB не попал в собранный образ

Проверка `log.txt` (внутренний подробный лог pmbootstrap) на этапе
финализации `/boot` (`boot-deploy`):
```
==> kernel: device-tree blob operations
ERROR: Unable to find qcom/sm7325-samsung-m52xq.dtb in the following locations:
    - /boot/dtbs*
    - /usr/share/dtb/
```
Ошибка НЕ фатальная (`pmbootstrap` продолжил и дошёл до `DONE!`), но
по факту наш собственный DTB отсутствует в собранном ядре целиком.
Список `boot/dtbs/qcom/*.dtb` внутри `linux-samsung-m52xq` APK
содержит СОТНИ файлов — все DTB апстрима `sc7280-mainline/linux` (Fairphone 5,
Fairphone 6, множество Chromebook'ов trogdor/herobrine, Sony Xperia и
т.д., включая даже `sm7325-motorola-dubai-csot.dtb` — чужой SM7325
телефон, уже смёрженный в апстрим), но `sm7325-samsung-m52xq.dtb`
среди них НЕТ.

**Причина найдена**: `linux-samsung-m52xq/APKBUILD` тянет исходники
не из нашего локального правленого клона
(`/home/sasha/Templates/майнлайн/linux/`), а качает ЧИСТЫЙ tar.gz
архив прямо с GitHub по фиксированному коммиту:
```
source="
	$pkgname-$_commit.tar.gz::https://github.com/sc7280-mainline/linux/archive/$_commit.tar.gz
	config-${pkgname#linux-}.$arch
	"
```
Наши правки (файл `sm7325-samsung-m52xq.dts` + строка в
`arch/arm64/boot/dts/qcom/Makefile`) существуют только в локальной
рабочей копии на диске и никогда никуда не публиковались — поэтому в
скачанном архиве их физически нет. Ядро в итоге собралось
успешно, но это чистый апстримный `sc7280-mainline/linux` без единого
байта наших изменений.

**Что это значит**: сборка полностью подтвердила, что весь конвейер
(APKBUILD, deviceinfo, packaging, `pmbootstrap install`) работает
правильно — но собранный образ пока НЕ содержит нашего устройства.
**Фикс на следующий раз** (не сделан в эту сессию): либо (а) запушить
наш `linux`-форк с правками на GitHub (свою ветку/форк
`sc7280-mainline/linux`) и указать в APKBUILD `source=` на неё, либо
(б) добавить наши изменения как `.patch`-файл рядом с APKBUILD и
подключить его через `source=`/`builddir`, что типичный подход
postmarketOS для локальных правок ядра без отдельного форка.

### Сверка ключевых параметров с реальным деревом LineageOS/downstream

Сравнение черновика `sm7325-samsung-m52xq.dts` с настоящим заводским
`m52xq_eur_open_w00_r05.dts` (из
`/home/sasha/kernel-droidian-experiment/sm7325/arch/arm64/boot/dts/samsung/m52/m52xq/`
— полный исходник downstream-ядра M52, уже использовавшийся в
параллельном Halium-проекте на этом же устройстве):

- **Платформа подтверждена**: верхнеуровневый `compatible` реального
  устройства — `"qcom,yupik-idp", "qcom,yupik", "qcom,idp"`, `model =
  "Samsung M52XQ PROJECT (board-id,05)"`. Совпадает с уже известным
  кодовым именем "yupik". **Уточнение для черновика**: наш DTS сейчас
  указывает `compatible = "samsung,m52xq", "qcom,qcm6490"` — стоит
  ДОБАВИТЬ `"qcom,yupik"` как fallback-запись, раз устройство само
  себя так идентифицирует.
- **Кнопка громкости вверх — ТОЧНОЕ совпадение**: в реальном DTS
  `vol_up.gpios` ссылается (через phandle `0x43`) на узел
  `qcom,pm7325@1 / pinctrl@8800`, `compatible = "qcom,pm7325-gpio"`,
  пин `6`, флаг `1` (ACTIVE_LOW), `linux,code = 0x73` (=115=
  `KEY_VOLUMEUP`). Наш черновик: `gpios = <&pm7325_gpios 6
  GPIO_ACTIVE_LOW>; linux,code = <KEY_VOLUMEUP>` — **это ровно то же
  самое, подтверждено байт-в-байт**. TODO-пометку "проверить под M52"
  для этой кнопки можно снимать.
- **PMIC-серия подтверждена**: реальное дерево использует `pm7325` и
  `pmk8350` (видно по узлам `qcom,pm7325@1`, `qcom,pmk8350@0`) — те же
  чипы, что уже подключены через `#include "pm7325.dtsi"` /
  `"pmk8350.dtsi"` в нашем черновике.
- **Панель подтверждена по имени**: реальное дерево содержит целых 5
  вариантов панели `nt36672e` (разные частоты — 60/90/120/144Hz,
  один вариант с DSC/cphy) под именами вида
  `qcom,mdss_dsi_nt36672e_fhd_plus_144_video`. Это ПОДТВЕРЖДАЕТ выбор
  `novatek,nt36672e` в черновике на уровне модели чипа, но точная
  compatible-строка и GPIO/supply всё ещё не перенесены (задача
  остаётся, т.к. downstream-дерево описывает панель через
  Samsung-специфичный `qcom,mdss-dsi-*` формат, а не через
  DRM-панель-driver формат mainline).
- **Регуляторы (самое рискованное место черновика) — сверить НЕ
  удалось напрямую**: downstream DTS вообще не использует
  mainline-схему `qcom,rpmh-regulators`/`regulator-name = "pm7325_s1"`
  и т.п. — Samsung-ядро работает с PMIC через полностью свою
  SPMI-регуляторную обвязку с другой структурой узлов. Прямого
  соответствия "взять число оттуда, вписать сюда" не нашлось за
  разумное время поиска. **Вывод не меняется**: `apps_rsc`
  regulator-таблицы в черновике (`vreg_s1b`/`vreg_l7b`/`vreg_l9b`)
  по-прежнему скопированы с Fairphone 5 БЕЗ проверки под M52 и
  остаются самым опасным нетронутым TODO.
- **WiFi-чип — не идентифицирован по этому файлу**: в реальном DTS
  нашлась только строка `esoc-name = "wlan"` (это узел
  подсистемы-модема/esoc, не конкретный WiFi SoC), явного
  `qcom,cnss`/`wcn6750`-подобного узла с моделью чипа в этом
  конкретном файле грепом не нашлось — видимо, WiFi-чип описан в
  отдельном dtsi/фрагменте, не в главном файле, либо задаётся
  Android-модулем `qca_cld3_wlan.ko` вне DTS (как уже установлено в
  параллельном Halium-проекте). TODO по WiFi остаётся открытым.

### Таблицы напряжений PMIC — сверены, новость хорошая

Изначально казалось, что сверить `vreg_s1b`/`vreg_l7b`/`vreg_l9b`
(скопированы в черновике с Fairphone 5) с M52 нельзя, т.к. в
board-специфичном `m52xq_eur_open_w00_r05.dts` они заданы в другой,
Samsung-фрагментной, форме. Но нашёлся более важный файл —
`yupik-regulators.dtsi` (в том же скачанном дереве, путь
`arch/arm64/boot/dts/vendor/qcom/`) — это **базовые SoC-уровневые
допустимые диапазоны напряжений для платформы yupik целиком**, не
привязанные к конкретному телефону-производителю. Раз наш M52 уже
подтверждён как `qcom,yupik` (см. выше), эти диапазоны — по
определению верхняя граница безопасности для ЛЮБОГО yupik-устройства,
включая M52.

Сравнение:
| Регулятор | В `yupik-regulators.dtsi` (допустимый диапазон) | В нашем черновике (из FP5) | Итог |
|---|---|---|---|
| `pm7325_s1` (vreg_s1b) | 1840000–2040000 мкВ | min=1840000 max=2040000 | **ТОЧНОЕ совпадение** |
| `pm7325_l9` (vreg_l9b) | 1200000–1304000 мкВ | min=1200000 max=1304000 | **ТОЧНОЕ совпадение** |
| `pm7325_l7` (vreg_l7b) | 2400000–3544000 мкВ (диапазон) | фиксировано 2952000 мкВ | **В пределах диапазона**, но точное значение под M52 не подтверждено отдельно |

Дополнительно проверено: board-специфичный fragment@101 в
`m52xq_eur_open_w00_r05.dts` (единственное место, где M52-дерево
трогает `apps_rsc`/регуляторы) переопределяет только
`rpmh-regulator-ldoc6` (ток срабатывания режима) — **NOT** l7/l9/s1.
То есть M52 не сужает и не переопределяет базовые диапазоны платформы
для этих трёх регуляторов — значит, значения из `yupik-regulators.dtsi`
действительно применимы напрямую.

**Вывод**: риск, которым была помечена вся секция `apps_rsc` в
черновике ("может повредить периферию при неверном напряжении"),
**существенно снижается для s1/l7/l9** — оба точных совпадения и
одно "в диапазоне" значение из независимого источника (SoC-платформа,
а не конкретно FP5) говорят, что скопированные с FP5 значения, скорее
всего, безопасны и для M52 (оба устройства на одной платформе yupik
используют одну и ту же допустимую сетку напряжений PMIC). Пункт TODO
в шапке черновика можно понизить с "опасно, точно неверно" до "скорее
всего безопасно, но l7 стоит уточнить точнее перед реальным тестом".

**Практический итог сверки**: 4 из ~7 TODO-пунктов в шапке черновика
(кнопка громкости, платформа/PMIC-серия, регуляторы s1/l9 точно +
l7 в допустимых пределах) можно считать подтверждёнными или
низко-рискованными. Экран подтверждён на уровне модели чипа, но не на
уровне GPIO/supply. WiFi, тачскрин, зарядка, камера, вибратор — всё ещё

5. **`pmbootstrap install` без `build --force` не пересобирает
   пакет**, если `pkgver`/`pkgrel` не менялись, даже если изменился

   --force linux-samsung-m52xq`.

### pmbootstrap: реальный pmaports-пакет устройства создан

Хост не имеет Python 3.9+ (только 3.8.10), а актуальный pmbootstrap требует
3.9+ — решено через Docker (`python:3.11-slim` + свой образ `pmb-env` с
предустановленными git/kpartx/procps/util-linux/e2fsprogs/dosfstools).
Внутри контейнера `pmbootstrap --as-root` (нормально в изолированном
контейнере). ВАЖНО: том `~/.config` обязательно монтировать отдельно,
иначе конфиг pmbootstrap теряется между запусками (не там же, где
`work`-директория).

Оригинальный `pmaports` теперь на `gitlab.postmarketos.org`, не
`gitlab.com` (проект переехал в 2024, старые ссылки/старые версии
pmbootstrap уводят на устаревший mirror).

**Создано через `pmbootstrap aportgen`** (реальный интерактивный визард,
отвечено: mainline/aarch64/Samsung/"Samsung Galaxy M52 5G"/2021/handset/
flash-method=none):

- `device-samsung-m52xq` (deviceinfo + APKBUILD) — `deviceinfo_dtb`
  указывает на `qcom/sm7325-samsung-m52xq` (наш черновик DTS)
- `linux-samsung-m52xq` (APKBUILD) — источник указан на наш форк
  `sc7280-mainline/linux`, конкретный commit (текущий HEAD на момент
  клонирования: `17425f528fe51fef6e86847e92baffab3b78623e`), конфиг —
  копия проверенного `fp5_defconfig`

Важная деталь синтаксиса `aportgen`, потраченное время на выяснение:
имя пакета должно быть `device-samsung-m52xq` (дефис), НЕ
`device/samsung-m52xq` (слэш) — слэш создаёт вложенную папку
`device/testing/device/samsung-m52xq` вместо плоской
`device/testing/device-samsung-m52xq`.

Копии обоих пакетов сохранены в `pmaports-device/` в этой же папке
проекта (`device-samsung-m52xq/`, `linux-samsung-m52xq/`).

**Не сделано в эту сессию**: реальная сборка (`pmbootstrap install`) —
это следующий шаг, скорее всего надолго (компиляция большого количества
пакетов с нуля для совершенно нового устройства). `sha512sums` в обоих
APKBUILD ещё не заполнены (`pmbootstrap checksum <pkgname>` для этого).

### О самом процессе установки (важное отличие от Halium-подхода)

Уточнено через реальную документацию по Fairphone 5 (тот же класс
устройства, зрелый порт):
- Для теста можно поставить rootfs **на SD-карту**
  (`pmbootstrap install --sdcard=/dev/sda`) + `pmbootstrap flasher boot` —
  внутреннее хранилище вообще не трогается.
- При установке на `userdata` рекомендуется `fastboot erase system`
  (система именно СТИРАЕТСЯ, не перезаписывается) + `fastboot reboot`.
- **`system`/`vendor`/`vendor_boot` в принципе не используются mainline-
  портом** — Android-стек полностью не нужен. Трогаются только `boot`
  (наше ядро+dtb) и `userdata` (наш rootfs). Это принципиально менее
  инвазивно, чем Halium-подход (там system.img патчится, vendor
  bind-mount'ится) — оборотная сторона в том, что весь Android-HAL
  недоступен, каждый драйвер нужен в mainline отдельно.
- Для нашего теста самый безопасный вариант — **`fastboot boot`**
  (временная загрузка из RAM, ничего не прошивается) — по сути "дуалбут
  без коммитмента": обычное включение грузит Android как обычно, Linux
  запускается только по явной команде с компьютера.

### Финальная тестовая сборка: WiFi + тач + дисплей + bluetooth + вибро

После находки про пропавший DTB (см. выше) и переноса правок в
собственный форк ядра (`sc7280-mainline-linux-m52xq`), в DTS
поочерёдно добавлены и подтверждены (компилируются, значения сверены
с реальным downstream-деревом M52 и/или платформенным yupik.dtsi):

- **WiFi** (WCN6750/`ath11k`) -- чип подтверждён через downstream
  defconfig (`CONFIG_CNSS_QCA6750`), узел уже есть в базовом
  `kodiak.dtsi`, добавлен `qcom,calibration-variant`. Board-
  специфичный калибровочный firmware (`bdwlan.elf`) уже есть локально
  (извлечён в параллельном Halium-проекте).
- **Тачскрин** -- Synaptics S3908 на i2c13 (QUP SE13) @ 0x4b, реальный
  irq-gpio (81) и supply (`vreg_l7c`, PM8350C LDO7) взяты из
  фрагмента@97 downstream-дерева. Протокол -- стандартный mainline
  `syna,rmi4-i2c` (auto-discovery функций); реальный протокол
  Samsung-прошивки (`sec_input`) может отличаться -- не проверено.
- **Дисплей** -- reset-gpio подтверждён (TLMM 44). Отдельная приятная
  находка: таймингы (hfp/hpw/hbp/vfp/vpw/vbp) И большая часть байт-кода
  init-последовательности в уже существующем mainline-драйвере
  `panel-novatek-nt36672e.c` совпадают с реальными downstream-данными
  M52 (60Hz-режим) практически один в один -- компилятор не патчился,
  compatible-строка оставлена как есть.
- **Bluetooth** (WCN6750-BT) -- узел уже есть в платформенном
  `yupik.dtsi` с ТЕМИ ЖЕ GPIO (85/86), что использует FP5 в mainline --
  перенесено на `&uart7` по образцу FP5.
- **Вибромотор** -- простой `gpio-vibrator` (TLMM 62), подтверждён
  downstream (`samsung,dc_vibrator`, COINDC).
- Добавлены поддерживающие regulator-узлы (`vreg_l19b/s7b/s8b` под
  PM7325, `vreg_s1c/l11c` под PM8350C) для bluetooth -- все значения
  из платформенного `yupik-regulators.dtsi`, не с FP5.

Правки закоммичены и запушены в
`korryasdlerto-lgtm/sc7280-mainline-linux-m52xq` (два снапшот-коммита
поверх первого: bluetooth+тач+wifi+дисплей, затем вибро). Полная
пересборка (`pmbootstrap build --force` + `pmbootstrap install`) прошла
успешно, `samsung-m52xq.img` обновлён.

Из него извлечены реальные `vmlinuz`/`initramfs`/наш `.dtb` и собран
`boot-m52xq-test-v1.img` (`mkbootimg`, Android boot image формат,
21 МБ, magic `ANDROID!` подтверждён) -- ЧИСТО ЛОКАЛЬНЫЙ артефакт,
НЕ прошивался и прошиваться пока не будет.

**Не проверено вообще**: гироскоп/акселерометр/приближение/освещённость
(не нашлись НИ В ОДНОМ источнике, включая настоящий клон LineageOS
`android_kernel_samsung_sm7325`, скорее всего висят за закрытым
sensor-hub протоколом без DT-представления). Камера, зарядка
(SM5714/PCA9468), отпечаток (Egis/ET-серия, протокол в закрытом
TEE-приложении) -- сознательно не начаты, отдельные большие задачи.
